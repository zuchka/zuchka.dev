The site is the message

This is the first post on zuchka.dev. The site itself is the topic. That's a self-indulgent way to start, but the choices baked into it are choices I want to be honest about up front, so future me can see what past me was thinking.

The site is hand-written HTML. There is no build step. There is no JavaScript framework. There is one shared CSS file and one HTML file per page. To publish a new post, I copy a template, rename it to a date-prefixed slug, and paste prose between <p> tags. To deploy, the static files get rsync'd to a server. It is, deliberately, the same setup I would have built fifteen years ago.

Why bother

Static-site generators are great. I've used them. For a docs site or a multi-author blog, an SSG is the right answer — markdown is faster to write than HTML, and a templating layer pays for itself the moment two pages share a navigation bar.

The thing is, this is a personal site. The cost-benefit looks different here. There are six pages. The "two pages share a navigation bar" problem is real — and I solve it with copy-paste. The cost is that updating the sidebar means editing six files instead of one. The benefit is that there is nothing else to update. No node_modules. No lock file rot. No "the build broke because a transitive dependency changed how it parses front-matter." The site is the source.

The most durable thing about a personal site is that nobody else cares about it. The web standards committee won't break my <ul> tags. My SSG's maintainer can't get bored and stop publishing security patches. The site has no dependencies because there is nothing to depend on.

The "developer cred" part

There's also a vibe argument. The site of a developer who works in plain HTML reads, to other developers, as a kind of confidence. I don't need a framework for this. View source on this page, and the page is what you see. There's nothing under the hood because there's no hood.

That's partly an aesthetic preference and partly a useful filter. The audience I want for this site — engineers and hiring managers — sees through the same lens. They will, if they're curious, view source on this page. I want what they find to look like care.

The cost

The cost is that posting is slower than it would be in markdown. Every paragraph is wrapped in <p>. Every list item is <li>. Code samples need <pre><code> and the HTML entities for &lt; and &gt;. The sidebar is duplicated across every page; if I add a new section, I edit it everywhere.

That's a real cost. I'm choosing to absorb it because I think the friction will keep me honest about what's worth posting. The thirty seconds of HTML tax is small, but it's real, and it has the same shape as the friction that makes me think harder before I publish a tweet that's already half-formed.

Maybe in a year I'll have written enough posts that the friction stops being a feature, and I'll port to an SSG. If that happens, the migration will be one regex per file. The whole point of plain HTML is that it's portable to anything else.

What's here

Four projects with their own pages: remove-markdown, the npm package that does ~800k downloads a week and that I almost never think about. DING, the alert engine I'm currently building. obsidian-readability, a small plugin. And PEGS, the peg solitaire game my father wrote in C in 1991 — the original MS-DOS binary, untouched, running in your browser through DOSBox emulation. That last one is my favorite.

And, going forward, more posts. If you want them in a feed: RSS works.
