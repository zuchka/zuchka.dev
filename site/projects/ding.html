DING

Don't store it. Stream it. DING it.

One binary that wraps your CI job, training run, or batch script — and pings you when it matters. Streaming alert engine for ephemeral compute. Currently in active development.

The 60-second pitch

Most monitoring tools assume your workload lives long enough to be scraped. Most CI jobs and ML training runs don't. DING is the alert engine that ships with your job, not next to it: rules in a YAML file, evaluated in-process, alerts fire during the run and a summary fires when it exits. Both die together. 

ding run -- npm test

That's the whole interface. Drop a ding.yaml next to your job, wrap the command, get pinged on Slack when something breaks.

Architecture

  • Single static binary — 5MB, no agents, no database, no cloud account.
  • Push-based, in-process — events emitted by your job, evaluated locally, alerts fire in <5ms.
  • Two modes — ding run for ephemeral jobs, ding serve for steady-state apps.
  • Auto-detects CI context — GitHub Actions, GitLab CI, CircleCI, Jenkins, Buildkite, Argo, MLflow, K8s. Branch, commit, run-id, actor — all attached to alerts automatically.

Why I built it

I kept hitting the same shape of problem: short-lived job dies, you want to know why, but Prometheus needs a target that lives long enough to be scraped, and standing up Alertmanager + retention + dashboards for a 4-minute CI step is more infra than the step itself.

Prometheus assumes a fleet. DING assumes a 4-minute CI job. The architecture difference is push vs. pull. Push wins for ephemeral compute.
